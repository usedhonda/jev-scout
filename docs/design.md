# Jev Scout: design brief

## 実装契約

- 共通正本は `skills/jev-scout/`。CC/Cdxから同じフォルダを参照する。
- キーは配布物の外に保ち、明示キー参照、Skill-local binding、環境変数の順に利用する。
- 初回にデータ範囲と実行上限を記録し、条件内では実験を繰り返し確認しない。JSONのapprovedフラグ自体をユーザー承認と見なさない。
- 合成動作確認・正解付き比較・実アプリ統合・本番運用を区別する。再試行も上限内、金額上限をリクエスト数で保証しない。
- 処理全体と単純な改善を比較し、調整用と最終評価用データを分ける。
- 実装は選択候補だけ。探索だけでは実装や公開を行わない。

CLIの正確な利用方法は共通Skillの実験手順を参照する。

## 追加調査からの改良

価値（既存改善・人手補助・新機能）と挿入形態（置換・意味条件追加・後段選別・競合解消・助言）を独立に扱う。固定分類・提案件数ノルマにはしない。強い候補には実際の挿入位置、呼出条件、最小導入、反証可能な比較を要求する。

出典付き選択は必要な用途だけに適用し、原文位置・候補漏れ・明示的な該当なしを確認する。根拠によるラベル補正は特定の不変条件を守るだけで正解保証ではない。段階導入やfail-openを万能規則にせず、実際の損失と行動で定義する。

評価は誤提案だけでなく有望候補の見落としも扱う。既存方式の条件付き補完を全体負荷で比較し、保存回答の再生を実測コスト削減と混同しない。対象版と確率分布の任意記録は既存CLIと互換に保つ。

## 合意済みの目的

リポジトリを読み、Jev を導入すると価値がある箇所を具体的な根拠とともに提案する。既存 AI モデルの代替や組み合わせだけでなく、現在 AI を使っていない工程と、現在は実装されていない有用な機能も探索する。Claude Code と Codex の両方で利用可能にする。

## 探索

- README、プロジェクト規約、設計資料、主要データモデル、入出力、利用者の操作を理解する。
- キーワード・正規表現・曖昧一致・分岐・順位付け・手動レビューを入口として、入力から判断、結果を使う処理まで追う。
- コードの複雑さだけでなく、人が繰り返している仕分け、記録内にある未活用の情報、意味的な検索・通知選別・照合などの新機能も調べる。
- 提案はファイル・関数・実際に存在するデータや操作に結び付ける。未実装機能は観測済みの不具合と混同しない。

## 適合性と価値を分ける

意味の理解が必要か、答えの候補を閉じられるか、誤り時の扱いを定義できるかを先に判断する。Choice / Noul / Score への分解を示す。

計算、厳密な識別子、スキーマ検証、認可、取引整合性は通常コードに残す。自由文生成や複雑な推論には別の方式を検討する。値の抽出は候補抽出をコード、意味的な候補選択を Jev とする組み合わせも評価する。

現行方式、単純な決定論的改善、Jev、必要なら LLM との複合案を比較する。Jev に適することだけを採用理由にしない。該当候補なしも有効な結論とする。

## 各提案の出力

- 現在の動作、場所、問題または新しい利用価値。
- 提案する変更、送る state、質問、コードに残す処理。
- 期待効果: 新しくできること、利用体験、精度、見落とし、手作業、保守、総費用、処理時間。
- 増える負担: 通信、API 費用、依存サービス、評価と運用の維持。
- 根拠を実測、前提付き試算、未検証仮説に分類する。頻度・単価・所要時間が不明なら数値を作らず、必要な情報を示す。
- baseline、評価データ、採用条件、導入を見送る条件。
- 低確信度、通信障害、古い入力に対する扱い。判断と副作用の実行を分ける。

例: 問い合わせのキーワード振り分けを Choice で補う。言い換え対応による再振り分けとルール保守の削減が期待できる一方、API 費用と通信待ちが増える。過去問い合わせで重大な誤振り分け、人手確認率、対応時間を比較する。実測前に削減率を断定しない。

## 実行段階の設計案

1. discover: 読取と候補提案。
2. validate: 質問、評価データ、baseline 比較を準備する。
3. implement: 選択した候補を最小統合する。

ユーザーの依頼範囲に沿って進める。探索のために対象リポジトリを Jev API へ送る必要はない。外部 API 実験では送信データと費用の許可を確認し、既存の明示許可があれば重ねて聞かない。

## 補足調査からの設計上の注意

- confidence は正解や認可を保証しない。閾値は対象データと誤りの影響に応じて評価する。
- 日本語など対象言語の実例を含める。英語のデモ結果をそのまま一般化しない。
- API 障害を意味判断の不確実性と区別する。fallback と再試行は対象処理に合わせる。
- モデル、質問、評価データの版を記録する。料金・制限・SDK は固定コピーせず統合時に確認する。
- 適用例と非適用例の両方で Skill の提案品質を確認する。提案件数を成功指標にしない。

## 共用構成

共通の Skill と参照資料を一つの正本にする。ホスト固有の設定・メタデータ・配布手順は必要な場合に CC/Cdx 別に置ける構造にする。既存 Skill の移設はこのプロジェクトの対象外。
