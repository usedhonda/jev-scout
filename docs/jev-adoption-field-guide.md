# Jev 導入の設計地図――意味判断を、どこに、どこまで置くか

**要旨**：既存ソフトウェアへのJev導入は、モデルの適用先を列挙する問題ではなく、意味の代理指標から実際の判断点を特定し、有限の出力・観測可能な証拠・副作用の境界を設計する問題である。四段階の調査を、置換以外の配置、制御平面、弱いセンサー、既存LLMの部分分解へ整理し、比較実験と非採用判断まで一続きに論じる。取り上げるOSSへの導入案は設計仮説であり、実測された改善ではない。

> **対象読者**：既存のソフトウェアに判断モデルを組み込む設計者・実装者。Jev の起動方法、認証、リクエスト構文の基本説明は扱わない。モデルが返す判断を、既存コードのどの責務と交換し、どこで交換しないかを扱う。

**構成**：第1〜6節で設計上の境界を整理し、第7節以降で実際のコードと評価へ適用する。候補の監査には第1・2・6・10節、制御系には第8節、既存LLMの部分置換には第10節が直接関係する。表だけをチェックリストとして使わず、各節の「なぜその境界か」を追う。

既存システムに Jev を入れるとき、最初に探すべきものは「分類器」でも「LLM 呼び出し」でもない。**人間が読み取る意味を、いま何が代用しているか**である。正規表現、HTTP ステータス、経過日数、XPath、規約パーサー、固定ラウンド数。これらはしばしば正しく安価な実装だが、ある境界では利用者の意図や業務上の状態を捉え損なう。そこが *semantic decision seam*――意味判断の挿入点になる。

ただし「曖昧な処理を見つけた」は採用理由にならない。有限の答えへ落とせること、入力に判別材料があること、誤判定の帰結を制御できること、単純なコード改善を超える価値があること。その四条件を満たすまで、Jev は導入候補ではなく調査仮説である。以下で挙げる OSS への統合案は、公開コードから導いた**未実装・未検証の設計仮説**であり、当該 OSS が Jev を採用したという意味ではない。公開デモや著者報告の速度・費用・精度も、別の運用環境へ外挿しない。

## 1. コードを「入力→判断→消費者」で読む

探索の単位は関数名ではなくデータフローだ。例えば `regex` を見つけても、それがメール引用の境界を決め、後段で最新返信の本文を削るのか、単なる表示上のハイライトなのかで価値と危険は違う。次の五点を一続きで特定する。

1. **状態の発生源**――誰が作り、どこまで信頼できるか。
2. **現在の代理信号**――正規表現、類似度、時刻、ステータス、モデル出力など。
3. **本当に知りたい性質**――「`error` という語があるか」ではなく「障害報告か」。
4. **結果の消費者**――表示、順位、通知、削除、承認、実行のどれか。
5. **失敗時の可逆性**――後で訂正できる助言か、見落としたら戻らない抑制か。

同じ意味判断でも、置き場所は複数ある。既存条件の**置換**、決定論的ルールに並ぶ**意味条件**、確定済みイベントの**後段フィルター**、競合・無該当時だけの**解決器**、人間への**助言**。価値（既存改善、人手補助、新機能）と配置は独立に考える。「Jev が適するから全面置換」ではない。公式の [System One の説明](https://docs.typesafe.ai/concepts/system-one) と [ユースケース地図](https://docs.typesafe.ai/concepts/use-case-map) も、判断をソフトウェアの制御フローへ組み込む構図を示す。

候補の入口は、`if/elif` や手書き taxonomy だけではない。第三の探索面は**制御平面**だ。何を検索するかより「もう検索を止めるか」、何を要約するかより「何を保持するか」、どの回答を生成するかより「次の LLM 呼び出しに進むか」。第四の探索面は**弱いセンサー**で、経過日数が担当者の責任を、HTTP 200 がアカウントの存在を、DOM の class 名が本文性を代用する場面に現れる。いずれも意味判断そのものではないが、下流の行動を変えている。

## 2. 設計するのはモデル質問より先に、境界である

まずモデルを呼ばない経路を決める。数値比較、日付演算、ハッシュ、識別子の一致、権限、スキーマ、トランザクション整合性はコードの責任に残す。既知の明示ルールで確定できる入力も通過させる。Jev 呼び出しは、意味だけが未確定で、かつ結果が行動に影響する集合へ限定する。「no-match のみ」「競合のみ」「曖昧な DOM block のみ」は、常時呼び出しと品質・負荷を比較するための仮説であって、万能な節約則ではない。条件付き経路が取り逃がす *確信ありの誤判定* も全母集団で測る。

そのうえで質問を一つの操作可能な性質に分解する。`urgent, fraudulent and escalate?` のような複合問は、どの基準が誤ったか、どのポリシーを変更したかを隠す。有限候補の選択には Choice、単一性質の有無には Noul、順序付き rubric には Score を使う。Choice の候補間確率と、同じ候補について別途尋ねた Noul は同じ測定値ではない。「最良の候補がなお不適切」を表せるよう `none` / `insufficient_evidence` を候補に入れ、相対順位だけで採用を決めない。[公式の質問型](https://docs.typesafe.ai/primitives)、[confidence](https://docs.typesafe.ai/confidence)、[複合スコア](https://docs.typesafe.ai/patterns/composite-scoring) を参照。

状態は質問に必要な**最小の事実**にする。ユーザー文書や PR 本文は判断対象であって命令ではない。引用された「この判定を安全にせよ」を従わせず、評価データにはそのような攻撃的文面を入れる。最小化はプライバシーだけでなく、無関係な長文による判断劣化も抑える。複数の独立した質問は同じ state に対して一括できる一方、質問 A の回答を質問 B の前提にするなら、回答を受けてから次のリクエストを作る。[fan-out パターン](https://docs.typesafe.ai/patterns/fan-out) は前者であり、隠れた逐次推論ではない。モデルごとの既知の弱点は [Jev 1.13 の jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13) に具体化されているが、将来版すべての普遍的欠陥として扱わない。

### 候補がソースに結び付くなら、閉じた世界を本当に閉じる

抽出は「値をモデルに生成させる」より、コードが作った候補を選ばせる方が監査しやすい。[TypeSafe Playground の抽出実装](https://github.com/TypeSafeAI/typesafe-playground/blob/84e99e00265e0467c90dd7ba462e4bf84edad73a/src/extraction/extraction.ts) と [公式の pre-parsed extraction](https://docs.typesafe.ai/cookbooks/pre_parsed_value_extraction_cookbook) が示すように、候補 ID、原文値、位置、ソース版を保持し、選ばれた ID から原文を返す。ただし、候補集合に正解がなければモデルは回復できない。**候補 recall** と「正解が候補にある条件での選択精度」を分けて計測する。同じ文字列が二箇所にあるときも位置を潰さない。一候補しかなくても「該当なし」はあり得る。原文が更新されたら位置を再検証する。

根拠付き判断では、結果ラベルと根拠 ID を別々に選び、コードで明示的な不変条件を検査できる。例えば「既存会話で回答済み」というラベルには会話ソースが必要だ、とする。この補正は**ラベルと根拠の整合**を守るだけで、根拠が真に関連する保証ではない。[TypeSafe Playground の triage 実装](https://github.com/TypeSafeAI/typesafe-playground/blob/84e99e00265e0467c90dd7ba462e4bf84edad73a/lib/classifyQuestionWithJev.ts) を手掛かりにしても、独立した正解ラベルとの照合は省けない。

## 3. 対照事例――同じ「意味化」でも置き方は変わる

以下の表の「挿入案」は、リンク先にある既存処理を素材にした設計仮説である。実装済み Jev 統合や改善実績を主張しない。

| 波・既存 seam | 狙う配置と残すコード | 比較すべきもの／重い誤り |
| --- | --- | --- |
| **初期：agent の操作選択**。生成モデルが操作判断と入力文生成を同時に担う | 有限の操作・対象 ID だけを判断し、任意文字列の作成は LLM、権限・引数検証・副作用はコードに残す。候補集合が動的なら対象 ID の失効も検査する | 単一 LLM、ルール dispatch、混成。誤対象への操作は「回答が速い」利益を打ち消す。[公式 function-calling cookbook](https://docs.typesafe.ai/cookbooks/function_calling) |
| **第二波：Huginn の trigger**。JSONPath で抜いた値を比較・正規表現等で判定 | 自然文フィールドにだけ semantic predicate を追加。既存の数値・一致判定、イベント生成は維持 | キーワード辞書、正規表現拡充。誤 trigger と見逃しを別計測。[固定版 `TriggerAgent`](https://github.com/huginn/huginn/blob/07163d4fbc3e8667dd68d711530e838677f88cf4/app/models/agents/trigger_agent.rb) |
| **第二波：変更通知**。正規化・差分の後、条件に応じ通知 | 差分自体は確定させ、関心事に合う変更かを後段で評価。重要変更を抑制する時は不確実・障害時の配信方針を先に定める | より良い CSS/regex と比較。通知件数だけでなく重大変更の未達を計測。[固定版 `processor.py`](https://github.com/dgtlmoon/changedetection.io/blob/fd7c9db23e371803bf1892b827b03d9c9c946bcd/changedetectionio/processors/text_json_diff/processor.py) |
| **第三波：context 保持**。長い agent 履歴を縮める | 「良い要約」を全面生成させるのでなく、どの発話・事実を保持するかの選択を補助。保持 ID、依存関係、容量計算はコードで扱う | 単純 recency、固定予算、既存の要約。圧縮率より、後続タスクで必要情報を失った率。[公開実験の README](https://github.com/tamaratran/fast-jev-compaction/blob/e3f262a7f4d42bd8dd32ced30d26176f7cb545b0/README.md) は著者の報告であり一般性能ではない |
| **第三波：テスト選択**。巨大なテスト集合を変更ごとに実行 | semantic impact を候補提示に使う。契約上必須のテスト、依存グラフで確定する範囲、最終 gate はコード/CI に残す | ファイル対応表、依存解析。速度だけでなく欠陥検出の取り逃がしを評価。[公開実験の README](https://github.com/mizchi/jev-test-filter/blob/01319cdc2bb897a91b90c5c1685359332a66bc21/README.md) |
| **第四波：soft-404**。サイトごとの HTTP 状態・文言・リダイレクトで profile の有無を推測 | 決定できないレスポンスで、可視本文に判別材料がある場合だけ意味的 fallback。`BLOCKED` と `UNKNOWN` を `AVAILABLE` と分ける | DOM selector/サイト別 fingerprint 改良。claimed/unclaimed が同じ内容なら**情報不足で非採用**。[固定版 Sherlock](https://github.com/sherlock-project/sherlock/blob/376018708c0f6948d3f978a9ae2915024e794654/sherlock_project/sherlock.py)、[除外サイト記録](https://github.com/sherlock-project/sherlock/blob/376018708c0f6948d3f978a9ae2915024e794654/docs/removed-sites.md) |
| **第四波：メールの返信境界**。行ごとの引用・署名・ヘッダー判定 | 既知の `>` 等は維持し、曖昧な fragment のみ `NEW_REPLY / QUOTE / SIGNATURE / HEADER / UNCERTAIN` へ分類。MIME、順序、出力組立はコード | 多言語 regex・クライアント別区切り。本文を消す誤りと引用を残す誤りを別計測。[固定版 email-reply-parser](https://github.com/zapier/email-reply-parser/blob/f67a872de3c7bebe3bd836afec60ab3f1201e8a6/email_reply_parser/__init__.py) |
| **第四波：stale issue**。最終更新からの経過日数で close を決める | 「次に行動すべき主体」を助言し、まず maintainer 待ち・不明ケースの**誤 close 抑止だけ**に使う。年齢、除外ラベル、権限、実際の close は既存コード | `needs-info` と最終コメント者の小さな状態機械。最重要指標は wrongful close。[固定版 actions/stale](https://github.com/actions/stale/blob/3467b6485bf80d2be20f30ec1a3d2d2aea0330e9/src/classes/issues-processor.ts) |

初期の発想を一件のサポート窓口で具体化すると、ユーザー文をいきなり「担当者へ転送」するのではない。既知の請求番号・契約 ID は厳密に照合し、残った曖昧な文章だけを `billing / product_failure / how_to / other` へ分ける。`product_failure` なら別の「稼働中の障害か」を尋ねてもよいが、緊急度と担当先を一問に混ぜない。誤転送の損失が大きければ低確信度は人手キューへ戻す。既存の keyword 改善と比べ、再振り分け率だけでなく、人手処理時間と provider 障害時の滞留を測る。この「有限判断はモデル、識別子と処理はコード」という原型が、後の各波へ受け継がれる。

第二波では、同じ原型が**新しい機能**にもなる。Huginn の自然文イベントに「顧客が解約を示唆している」という条件を追加するなら、現在の JSONPath と数値条件を置換する理由はない。対象フィールドの値と最小限の文脈を Noul へ送り、既存の rule engine が他の条件と合成する。逆に changedetection.io では、差分をモデルに探させない。コードが検出済みの変更行と「価格改定だけ知りたい」という購読者の関心を与え、通知直前で選別する。前者は**意味条件の追加**、後者は**確定イベントの後段ゲート**。両者を「分類機能」と一括りにすると、重要変更を誤抑制する後者固有の失敗を見失う。

第三波の代表は検索の**終了時点**だ。[deep-searcher の固定版評価素材](https://github.com/zilliztech/deep-searcher/tree/ddc36db317836bd42302b36f03166bec5324708d/evaluation/jev_stopping) が扱う問いは「検索結果のどれが関連するか」だけではない。質問と蓄積済み証拠を見て「これ以上検索しなくても根拠付き回答が可能か」を判断する。固定三ラウンドなら単純だが、簡単な質問には無駄、難問には不足し得る。Jev の停止提案を採る場合も、最大ラウンド・時間予算・出典照合・回答生成はコードに残す。比較対象は固定ラウンドと簡単な heuristic と LLM 停止判定。評価軸は停止判断の一致率ではなく、**早すぎる停止で失った回答根拠**、最終回答の品質、全処理時間である。著者報告の局所的な速度値はこの一連の性能を証明しない。

第四波の stale issue は、第三波と同じ制御判断をさらに具体的な**弱いセンサー**から発見する。`days-before-close` は経過時間を測れるが、今だれの返答を待っているかは測れない。最終コメントが maintainer の質問なら `needs-info` label で十分かもしれない。一方、自由文のやり取りでは「再現を待つ」「修正は maintainer 側」「解決済み」の区別が残る。そこで履歴の短い抜粋を読ませ、`WAITING_ON_AUTHOR / WAITING_ON_MAINTAINER / RESOLVED / UNCLEAR` を提案させる。ただし Jev が `WAITING_ON_AUTHOR` と答えたことを close 許可にしない。最初は `WAITING_ON_MAINTAINER` と `UNCLEAR` の誤 close 抑止だけに使い、再開された issue と人手判定を照合する。この片方向性が、単なる「分類精度」より大きな設計判断だ。

第二波の根拠付き抽出と第三波の制御平面は異質に見えるが、共通するのは「モデルに作業全体を渡さない」ことだ。抽出では ID 選択だけ、検索では停止判断だけ、テストでは候補提案だけ、stale issue では close 抑止だけに留める。その狭さが評価可能性を作る。一方、狭いほど候補生成や呼出条件の誤りが支配的になる。モデル単体の正解率だけで導入を決めてはいけない。

### 一つの LLM 呼び出しを分解する

第四波の別の発見は、すでに LLM があるからといって全面代替を考えないことだ。[Mem0 の固定版プロンプト](https://github.com/mem0ai/mem0/blob/f8082a7345dadd9e042ebbc40b57b1498c8f6d63/mem0/configs/prompts.py) には、記憶に対する `ADD / UPDATE / DELETE / NONE` 型の遷移と、記憶本文の作成という異なる仕事が含まれる。候補 ID の選択や遷移だけを Jev に切り出し、本文生成は LLM に残す、という分解は試す価値がある。しかし、プロンプトが存在することは現行プロダクトの主経路である証明ではない。caller と版を追い、誤 `DELETE`・誤 `UPDATE` を強く重み付けして比較する。記憶の削除を確率値だけで直接実行しない。

同じ分解は release 判定にも効く。[commit-analyzer の固定版](https://github.com/semantic-release/commit-analyzer/blob/1dbd3a049092dfc0cd9af94d25895af0131837ca/index.js) のように明示ルールと規約パーサーがある場合、規約外の commit だけを意味的に扱う余地はある。ただし `fix stuff` のように入力に影響が記されていないなら、どのモデルにも SemVer の根拠はない。規約遵守そのものが製品・組織契約なら、fallback より lint とルール整備が正しい。

### 設計を一件、終端まで通す――stale issue の誤 close 抑止

実務で最も難しいのは、候補を発見した後にモデルの責任を小さく固定することだ。stale issue を例に、まず現行の行動を分解する。日数・除外ラベル・closed/locked 状態はコードが判定する。その後「一定期間の更新がない」という観測を「対応不要」とみなし、コメント・close へ進む。この最後の推論だけが弱い。経過時間は正確でも、**誰が次に行動するか**を示さないからだ。

最初の変更案は close 判断の置換ではなく、既存の close 候補に対する片方向の拒否権である。適格性を通った issue について、title、本文の短い抜粋、直近コメントの順序・投稿者の役割、既存ラベルを最小 state とし、`WAITING_ON_AUTHOR / WAITING_ON_MAINTAINER / RESOLVED / UNCLEAR` を問う。`WAITING_ON_MAINTAINER` または `UNCLEAR` なら自動 close を保留し、人間の確認キューへ戻す。それ以外でもモデルの答えだけでは close を許可せず、従来の決定論的条件を満たしたものだけが既存処理へ進む。権限、実際の API 操作、再実行時の冪等性もモデルの外だ。

この案にはモデルを使わない対抗馬がある。`needs-info` ラベルがあり、最後の maintainer コメントが再現情報を求めていて、その後 reporter が答えていない場合だけ close する、という役割ベースの状態機械だ。この単純な対案で誤 close が十分減るなら、外部サービスを足す理由は薄い。また直近コメントだけでは「修正待ち」と「情報待ち」が区別できないなら、state の増量で解けるか、そもそも観測可能な情報が足りないかを切り分ける。全文を無条件に送るのは答えではない。

評価集合には、過去に bot が close した後で再開された issue、maintainer が未回答のまま残った issue、reporter が質問へ未回答の issue、明示的に解決した issue を別々に入れる。人手ラベルは「次の責任主体」と「close してよかったか」を独立に付ける。比較するのは age-only、ラベル＋最終コメント者ルール、Jev 抑止ゲートの三つ。主指標は全体一致率ではなく、**誤 close の削減**と、そのために増えた保留件数・人手時間だ。自信が高い誤 close は別に抽出する。API 障害、候補外回答、証拠不足は保留へ落とし、障害時に close が増えないことを注入テストで確かめる。

この設計は、Jev が責任主体を正確に読めるとまだ証明していない。shadow で同じ履歴に判断だけを記録し、現行処理との食い違いを人間が盲検で評価して初めて、抑止へ進む意味が生まれる。もし単純な状態機械と差がなければ見送る。導入判断の完成形とは、モデルを使うことを確約した仕様ではなく、**比較の結果で採用を撤回できる仕様**である。

## 4. 評価は「平均正解率」から始めない

採用判断に必要な単位は**最終行動**だ。歴史的データに正解を付け、現行実装、単純な決定論的改善、Jev を同じ holdout で比べる。必要なときだけ LLM・混成を加える。調整用と最終評価用を分け、モデル ID・質問版・閾値版・候補生成版・ソース版を保存する。実験用 alias が移動すれば、かつての閾値と再現性は失われる。閾値は他案件から輸入せず、実際に起こる誤りの損失とラベル付きデータで決める。

結果は少なくとも三層に分ける。**候補生成**では正解が選択肢に入った率、**条件付き判断**では候補が揃った場合の選択と校正、**end-to-end** では呼出条件・モデル・fallback を通った最終行動。たとえば抽出で candidate recall が低いのに質問文だけ磨いても上限は動かない。no-match のみ呼ぶ設計なら、no-match 判定器が誤って確信したケースも集計する。オフライン再生で推定できるのは呼出件数であり、本番の p95 遅延や請求額ではない。

損失は対称でない。変更通知の見逃しと余計な通知、メール本文の欠落と署名混入、stale issue の誤 close と残存、記憶の誤削除と冗長な保持は別指標にする。Score の一致率を一つ示すより、損失の大きい分岐の precision/recall、棄権率、人手負荷、事後訂正率を見せる。confidence は正解でも認可でもない。**高 confidence の危険な誤り**を hard case として残す。[公式の confidence routing](https://docs.typesafe.ai/patterns/confidence-routing) も、人間や別経路へのルーティングを含む設計である。

実験前に、反証条件を書く。「regex 拡張が同程度の重大変更 recall を低い負担で達成したら不採用」「soft-404 の claimed/unclaimed に可視差分がなければ不採用」「テスト選択で重大欠陥を一つでも落とすなら自動 skip はしない」。この条件がない候補は、成功指標を後付けしやすい。生産環境への一手目は用途ごとに異なる。人間がキューを読むなら順位表示が完成形にもなる。通知抑制や自動 close のように未達が戻らない処理では、shadow・助言・抑止専用を選べる。全候補に一律の四段階ロールアウトを強制しない。

## 5. 故障時の行動を「fail-open」で済ませない

少なくとも四つを区別する。**証拠なし**、**判断が不確か**、**回答が候補外・不正**、**通信障害**。これらを一つの低スコアへ押し込むと、障害が誤承認や誤抑制に化ける。fallback は実際の行動名で定義する。

| 消費者 | 不確実・障害時の具体行動 | 理由 |
| --- | --- | --- |
| 承認・権限境界 | 承認しない。人間または既存の厳密な認可へ戻す | モデル出力は権限を付与しない |
| 重要変更の通知選別 | 変更を配信する、または保留キューに残す | 既存 keyword filter へ戻して重要変更を黙って落とすのは「fail-open」ではない |
| Stale issue の close 抑止 | close せず保留する | 誤 close の損失が追加レビューより大きい場合 |
| 検索停止・context 削減 | 既存の上限・保持ルールを実行する | 無制限継続や必要情報の不可逆削除を避ける |

どれが正しいかは用途と損失に依存する。外部サービスの遅延・可用性・課金、入力の機密性、地域・規約、ログ保管も統合コストに含める。原文全体を送らず excerpt と不透明 ID に絞り、必要な機密や個人情報を除く。サードパーティ文書を state に入れるなら、その中の指示は命令ではない。リトライは副作用の二重実行を起こさない境界で管理する。モデルが返した候補 ID は現在のソース版に存在するか再検証してから使う。

## 6. 「導入しない」を精度の高い結論にする

もっとも強い非適用は、曖昧さではなく**契約の性質**から来る。[Black の固定版 formatter](https://github.com/psf/black/blob/2b96e280653fd79f593c942191d8614ca6ce39e6/src/black/__init__.py) に読みやすさの主観はあっても、製品価値は同じ版・同じ設定から正規化された出力を再現することだ。複数の正しい整形候補から毎回意味的に「良い方」を選ぶ設計は、その契約を壊す。別製品として助言を作るなら別の課題であり、formatter の置換案ではない。

ハッシュ、SemVer の順序、日付比較、ACL、JSON/schema validation、厳密な終了証明も同様に通常コードへ残る。高頻度・低遅延のストリーム境界（例：[Vector の固定版 line aggregator](https://github.com/vectordotdev/vector/blob/511b03128da4d0d8c365f38956e72acf2cff2420/src/line_agg.rs)）は意味上は候補でも、remote call を hot path に置く予算が成立しないかもしれない。さらに、入力が claimed/unclaimed で同一なら、意味モデルにも情報は増えない。**人間が同じ入力から区別できるか**を先に問う。否なら必要なのは別の観測手段である。

最後に、採用しない理由を「Jev 不向き」で止めない。単純なルール改善で十分、候補 recall が不足、データ外部送信不可、誤りの救済経路なし、追加遅延に見合う価値なし、現行契約が決定性を要求――どれなのかを書く。逆に採用候補には、具体的な挿入位置、呼出条件、最小 state、棄権経路、コードに残す不変条件、反証可能な比較を一枚の設計として示す。Jev を多く置くことではなく、**意味判断の価値がある一点だけを、検証可能な形で置くこと**が導入の技術である。

## 7. 挿入点を見つける技術――名前ではなく「代用品」を探す

実際のリポジトリには `semantic_decision()` という親切な関数はほとんどない。判断は、文字列を拾う正規表現、`unknown` へ落とす例外処理、定数で決めたタイムアウト、巨大な switch、集計後の「最初の一件を採る」処理に埋まる。したがって探索は「AIを探す」でも「classifierを探す」でもなく、**業務上の性質が別の観測量で代用されている場所を探す**作業になる。

例えば次の架空の運用を考える。価格監視サービスがWebページを取得し、前回との差分があれば通知する。差分は正確だが、広告欄や更新日時の変更でも通知される。ここで `diff` をJevに置き換えるのは誤りだ。差分は「何が変わったか」という検証可能な事実を提供している。弱い代理信号はその後の「何か変わったなら、その人にとって重要なはず」という推論である。ユーザーが求める「この商品の購入可能性が変わったか」という意味を、単純な変更検出が代用している。この場合の挿入点は **差分の後、通知の前** だ。[changedetection.io の固定版処理](https://github.com/dgtlmoon/changedetection.io/blob/fd7c9db23e371803bf1892b827b03d9c9c946bcd/changedetectionio/processors/text_json_diff/processor.py) は、この種のデータフローを読む素材になるが、同製品でのJev改善は未実証である。

探索で重要なのは、言い換えた業務上の問いが本当に有限であるかだ。「なぜ変わったかを説明せよ」は自由文生成である。一方「既知の在庫状態が `AVAILABLE / UNAVAILABLE / UNCERTAIN` のどれへ移ったか」は有限状態であり、通知条件に直結する。元HTMLを丸ごと渡す前に、現行の抽出器が作った前後の製品名・価格・在庫表示・タイムスタンプと、差分周辺の短い抜粋で足りるかを問う。もしページがログイン画面しか返さなければ、情報が足りない。`UNCERTAIN` はモデルの弱さの告白ではなく、観測できない世界について勝手に断定しないための製品状態である。

### 検索語からデータフローへ

リポジトリを読む最初の30分では、次の語族を入口にできる。ただし一致した行を候補として報告してはならない。**呼び出し元、入力の生まれる場所、判断後の消費者**を辿って初めて一つの候補になる。

| 入口になる語族 | 疑うべき代理関係 | 辿るべき消費者 |
| --- | --- | --- |
| `regex`, `substring`, `contains`, `pattern` | 表記が意図や文書構造を代理 | 抽出値、ルーティング先、表示除外 |
| `status`, `redirect`, `errorMsg`, `WAF` | 通信上の成功が業務上の成功を代理 | account存在判定、取引結果、再試行 |
| `updated_at`, `stale`, `age`, `timeout` | 時間が責任・価値・完了を代理 | close、保持・削除、検索終了 |
| `unmatched`, `default_rule`, `releaseRules` | 規約への一致が人間の意味を代理 | release影響、分類、レビュー |
| `prune`, `discard`, `XPath`, `link_density` | DOM構造が本文性を代理 | 要約・検索に残る原文 |
| `enum`, `event`, `action`, `target_id` と生成文の混在 | 生成モデルが有限判断まで同時に担当 | DB更新、ツール実行、配信 |

探索語の選択より「その代理信号を外したら、利用者に何が変わるか」の方が重要だ。`timeout` は単にソケットを守る上限かもしれないし、人が話し終わったかを推測する境界かもしれない。前者は意味モデルの仕事ではない。後者は候補になり得るが、リアルタイム経路に追加通信を入れられるとは限らない。同じ単語から逆の結論へ至るため、**コード形状だけで提案を量産するScoutは弱い**。

### 反例を先に探す

候補に見えたら、その場で三つの反例を作る。第一に、**単純な規則で直る反例**。メール引用なら別クライアントの既知ヘッダーを追加するだけで十分かもしれない。第二に、**入力に答えがない反例**。ログイン画面しか見えないプロフィールは本物と不存在を区別できない。第三に、**確率化が契約違反になる反例**。formatterが同じ入力から毎回同じ出力を作る約束は、曖昧な好みとは別の製品価値だ。反例が強ければ候補を下げ、必要なら「追加観測」「規則改善」「非採用」へ結論を変える。

これが初期調査から第四段までの発展である。最初はLLMや手書きルールの代替を広く探した。次にsidecar、後段ゲート、競合時だけの解決器が見えてきた。第三段で検索・保持・テストといった**処理そのものの進行**を対象にし、第四段では「HTTP statusや経過日数のような小さな代理指標」に再び降りてきた。抽象化して広く見る眼と、具体的なコードへ戻る眼を往復させる。

## 8. 制御平面――何を計算するかを判断する

分類は通常、一件の入力へラベルを返す。制御平面の判断は、次にどの計算を行うか、いつ止めるか、どの状態を残すかを変える。したがって誤判定がもたらす損失は「ラベル違い」ではなく、**まだ必要な証拠を読まなかった、唯一の正解候補を捨てた、必須テストを走らせなかった**という機会損失になる。ここは第三段調査の中心だが、効果を語るには下流の成果まで測らなければならない。

### 検索を止める

ある質問に対して検索器が毎回三ラウンド読むとする。簡単な質問には無駄で、反証を含む難問には不足する。`STOP / CONTINUE` を質問すればよさそうだが、まず「十分な証拠」の意味を定義する。少なくとも主張に対応する出典IDがあり、反証の可能性をどこまで見たかが分かり、回答生成側が出典を実際に引用できる状態が必要だ。単なる上位文書の語彙一致を十分性と見なせば、検索を一回早く終えるだけで誤答が増える。

導入案では検索・再ランキング・引用チェックを既存コードに残し、各ラウンド後の累積証拠だけから停止の助言を得る。ハード上限は別に維持する。データセットは単純問、複数資料の統合問、最初の資料が後の資料で否定される問、情報がなく答えられない問に分ける。比較は固定ラウンド、単純なヒット数/スコア閾値、Jev判断、必要なら既存LLM。停止判断の正解率だけでなく、最終回答の根拠欠落、不要検索、総時間、API失敗時の挙動を測る。[公開の探索実験](https://github.com/zilliztech/deep-searcher/tree/ddc36db317836bd42302b36f03166bec5324708d/evaluation/jev_stopping) は配置を考える手掛かりであり、その結果を別システムの性能予測に使わない。

### 何を残すか

コンテキスト圧縮では「短い要約を作る」ことより「後で必要な事実を消さない」ことが難しい。ツール呼び出しと結果、ユーザーの制約、未解決の疑問、更新された古い情報には依存関係がある。最初に要約対象を `full / pointer / omit` のような保持状態へ分類する場合も、選択単位と復元先をコードが管理しなければならない。古いという理由だけで最新の設計制約を捨てたり、新しいという理由だけで無関係なログを残したりしてはならない。

評価も圧縮率では足りない。同じ後続タスクを、原文履歴、単純なrecency、既存要約、選択的保持の各条件で続行し、制約違反、再検索、ツール再実行、最終成果を比べる。選択で残ったポインターが読めない場合も失敗として数える。キャッシュに残っていても元資料が更新されたなら鮮度確認を要する。[選択的保持の公開実験](https://github.com/tamaratran/fast-jev-compaction/blob/e3f262a7f4d42bd8dd32ced30d26176f7cb545b0/README.md) に報告された削減率を、そのまま自分のタスク成功率へ変換してはいけない。

### どの計算を走らせるか

CIのテスト選択は、実行時間が測りやすいため過大な期待を生みやすい。ファイル所有表なら変更ファイルに対応するテストが選ばれ、依存解析なら静的な伝播が分かる。しかし変更が公開APIの意味を変え、離れたモジュールの契約テストを破ることもある。Jevの役割を「影響しそうなテストの助言」から始め、保護必須チェックや、マップできない変更・focused test失敗時のフル実行を残す。評価には過去の実際の失敗を含む変更を使い、**省けた実行時間と取り逃がした欠陥**を同時に数える。単なる「変更説明とテスト名の似ている度合い」は代用指標にすぎない。[テスト選択の公開実験](https://github.com/mizchi/jev-test-filter/blob/01319cdc2bb897a91b90c5c1685359332a66bc21/README.md) は探索の材料になるが、自動skipの安全証明ではない。

### 探索木と生成器の評価

合法な次状態がコードで列挙される探索器では、意味判断を候補順序のpriorに使える。勝手に合法手を生成したり、最短経路を「たぶん正しい」と証明したりはできない。探索予算が限られる場合、順序変更によって唯一の解に到達する前に予算が尽きることもある。したがって固定seedの探索問題を使い、成功率、探索ノード数、正解到達までの時間、解の最適性を分けて測る。生成された作品や文章の評価器として使う場合も同じで、rubricへの過適合が起こり得る。モデル評価値だけが上がり、人間の独立評価が下がるなら、評価関数を攻略された可能性を疑う。

この章の結論は、制御平面がJevに向いているという単純なものではない。**有限判断が計算の途中に存在する**ことと、**そこへ外部判断を挟む利益が上流・下流を通して残る**ことは別である。構造を見つけた後に、削られた計算が失った価値まで測る必要がある。

## 9. 弱いセンサーの解剖――第四段調査を使う

「意味の代用品」は、単に精度の低い実装を指さない。安価で説明しやすく、ほとんどの入力で十分働くが、ある分布で取り違える観測量を指す。HTTP status、正規表現、経過時間、XPathはそれぞれ違う対象を測っている。問題が起こるのは、測ったものをそのまま**製品が必要とする意味**へ昇格させる瞬間だ。第四段の各ケースは、Jevを入れるならその瞬間に限定すべきことを示す。

### 「HTTP 200」を「存在する」と読まない

[Sherlock の固定版](https://github.com/sherlock-project/sherlock/blob/376018708c0f6948d3f978a9ae2915024e794654/sherlock_project/sherlock.py) は、サイトごとにmessage、status code、redirect URLなどを用いてusernameの有無を推定する。WAFを示す定型文も検出する。これは雑な実装というより、サイトの異なる仕様を、共通の結果型へ接続するための現実的な設計だ。ただし200が返っても中身がsoft-404、ログイン要求、bot対策、実在プロフィールのいずれかというサイトでは、プロトコルの成功と業務上の存在が分離する。[除外サイトの記録](https://github.com/sherlock-project/sherlock/blob/376018708c0f6948d3f978a9ae2915024e794654/docs/removed-sites.md) は、この限界を理解する一次資料になる。

Jevを試すなら、まず確実な404、明白なWAF、明示的なprofile IDといった既存の強い判定は維持する。曖昧なレスポンスに限り、title、正規化した可視本文の短い抜粋、最終URL、サイトの既知の状態を渡す。候補は `CLAIMED / AVAILABLE / BLOCKED / INDETERMINATE` のように業務上異なる後続行動へ対応させる。`BLOCKED` を `AVAILABLE` へ混ぜればbot対策を存在しない利用者と誤解し、`INDETERMINATE` を省けば判別材料のないサイトで断定を強いられる。

ここで最初の評価はモデル比較ではなく**可観測性テスト**だ。同じサイトの既知claimed/unclaimedペアを集め、HTTP status、URL、本文、レンダリング後のDOMのどこに差があるかを確認する。もし同じログイン画面しか取得できなければ、Jev実験に進まない。必要なのは許可された別の観測手段か、サイト非対応の明示である。差があるなら、まずCSS selectorやサイト固有fingerprintの改善をベースラインにし、それが崩れるlong-tailケースでのみ意味判断を比較する。false claimed、false available、WAF誤認、unknown率を別に扱う。性能以前に、この分解を欠いた「アカウント存在分類器」は問題を取り違えている。

### 行の境界を、文書の境界と混同しない

[email-reply-parser の固定版](https://github.com/zapier/email-reply-parser/blob/f67a872de3c7bebe3bd836afec60ab3f1201e8a6/email_reply_parser/__init__.py) は、引用ヘッダーや `>`、署名の手掛かりを使い、返信本文をfragmentへ分ける。この結果は単なるラベルではない。ヘルプデスクが「顧客の新しい返答」として保存・要約する文面を決める。本文を引用と誤認して削る損失と、過去の引用を新しい要求として残す損失は違う。

Jevの提案はメール解析全体の置換ではない。MIME decode、文字コード、改行正規化、既知の引用記号やクライアント固有区切りは現行実装に残す。そのあと、曖昧なblockに限って前後数行と現在のfragment状態を与え、`NEW_REPLY / QUOTED_HISTORY / SIGNATURE / HEADER / UNCERTAIN` を選ぶ。答えを一行ずつ出すより、まとまりのあるblockで判断した方が「On ... wrote:」の言語差や手書き引用を捉えやすい可能性がある。しかし、どの単位がよいかはラベル付きfixtureで検証するしかない。言語・メールクライアント・モバイル署名ごとに分け、最終的な抽出本文のexact matchと重要文の欠落を測る。

ここではデータ許可が候補を一瞬で覆す。メール本文を外部サービスへ送れない環境なら、たとえオフラインfixtureで高精度でも導入しない。メールアドレスや署名をredactしても、本文そのものが機密を含み得る。入力を小さくしたから安全、と自動的には言えない。送信できるデータ分類、保持ポリシー、利用者への説明が設計の一部になる。

同じ「境界」でも、[Vector の固定版line aggregator](https://github.com/vectordotdev/vector/blob/511b03128da4d0d8c365f38956e72acf2cff2420/src/line_agg.rs) では条件が変わる。ログの一行が前のeventに続くかを誤ればsplit/mergeの失敗になるが、高頻度ストリームでは一行ごとの外部呼び出しが処理量と遅延の予算を破るかもしれない。低頻度の異種ログimportでは比較に値する一方、標準スタックトレースをtimestamp/indentで処理できるならモデルを足す理由は薄い。意味的に解けそうな問いと、運用的に呼べる問いは同一ではない。

### 規約が拾わなかった「意味」をどう扱うか

[commit-analyzer の固定版](https://github.com/semantic-release/commit-analyzer/blob/1dbd3a049092dfc0cd9af94d25895af0131837ca/index.js) は、規約に沿うcommit messageや明示ルールからrelease impactを決める。`BREAKING CHANGE`などの明示は、その組織の手続きを含む強い証拠である。Jevの余地があるとしても、規約に一致しないが意味の記されたcommitをどうするかという狭い部分だ。例えば「remove legacy authentication endpoint」は互換性の影響を示唆するが、`fix stuff` は何も語らない。後者へMAJOR/MINOR/PATCHのどれかを強制すると、モデルの流暢さが証拠不足を隠す。

設計時にまず決めるのは、規約外commitを許す組織なのか、規約遵守そのものが契約なのかだ。後者ならcommitlintやPRテンプレートを改善する。前者なら、unmatchedのうち十分な説明があるものだけ意味判断を試す。最終versionの計算、手動override、publishはコード・人間の権限に残す。比較ではunder-bumpとover-bumpを別に数え、messageに記述されていない互換性破壊は対象外として明記する。この場合の根本課題はモデル能力でなく**変更の意図が記録されているか**だ。

### 「古い」を「誰も待っていない」と読む危険

[actions/stale の固定版](https://github.com/actions/stale/blob/3467b6485bf80d2be20f30ec1a3d2d2aea0330e9/src/classes/issues-processor.ts) では日数・ラベル・状態を使ってstale化やcloseを進める。第四段調査が見たのは優先度スコアではない。「次に動く責任がreporter、maintainer、誰にもない、あるいは不明」のどれかというworkflow stateだ。単に古いissueでも、maintainerが修正を約束してから放置したものと、reporterへ再現手順を頼んだまま返事のないものでは、closeの意味が違う。

第3節の詳細設計で片方向の抑止を選んだのはこのためだ。モデルの誤読で余分に残るissueは、人間が後から片付けられる。一方、誤closeは追跡を断ち、参加者へ「報告は不要だった」と伝える。損失が非対称なら、同じ分類器を使うとしても、使ってよい方向を制限する。これは閾値を高くすればよい話ではない。**モデル結果へ与える権限**を先に狭める設計だ。

### DOMを捨てる前に、残す理由を見る

[Trafilatura の固定版抽出器](https://github.com/adbar/trafilatura/blob/c852cae9708a59f04521b19395d8ed49771a5c78/trafilatura/main_extractor.py) は、XPath、link density、nodeの位置関係などを使って本文を抽出する。DOMのclass名やリンク率は、本文として必要かを示す手掛かりだが、テンプレートが変わると境界が揺らぐ。ここで全文をJevへ渡して書き直させると、原文の保存・出典・順序という抽出器の価値が失われる。

代わりに、コードが明らかなscript/navを除去して作った**曖昧なnode集合**を入力にする。node ID、短い本文、見出し、親・隣接nodeの抜粋から `MAIN_CONTENT / RELATED / PROMO / METADATA / UNCERTAIN` を選び、コードが元nodeを保持または除外する。candidate recall、本文欠落、広告混入、caption喪失を別々に測る。単純なXPath更新やReadability系の改善が同じ効果なら採用しない。大量クロールで一nodeごとに通信する案は、精度が良くても費用やスループットで失格になり得る。曖昧なページだけまとめて判断する配置まで含めて評価する。

弱いセンサーの共通式は `proxy -> bounded meaning -> action` だ。しかし成功例の共通実装はない。Sherlockは証拠の有無、メールはプライバシー、releaseは規約文化、Vectorはhot path、staleは不可逆な行動、Trafilaturaは原文忠実性がそれぞれ支配する。候補の「型」が同じでも採用判断が同じとは限らない。

## 10. 一つのLLM呼び出しを分解する――操作と文章を切り離す

既存の生成モデルを見たとき、「Jevのほうが速いか、安いか」と丸ごとの置換比較を始めると重要な構造を見落とす。一つの応答に `operation: UPDATE`、`target_id: 42`、`new_text: ...` が含まれるなら、前二者は既知の集合からの判断、最後は新しい文面の作成だ。同じモデルが返していても、別の品質基準・別の失敗時動作を要する。第四段の[Mem0固定版プロンプト](https://github.com/mem0ai/mem0/blob/f8082a7345dadd9e042ebbc40b57b1498c8f6d63/mem0/configs/prompts.py) は、この分解を考えるよい素材である。ただし、ファイルにあるpromptが現在の本番主経路であるとは限らず、active callerの確認が先だ。

記憶更新を例に、利用者が「最近は別の都市に住んでいる」と話したとする。候補記憶には古い居住地、旅行先、同名の別人についての記述があるかもしれない。Jevが担当できる仮説は、新事実と候補の関係を `ADD / UPDATE / DELETE / NONE` から選び、更新対象なら候補IDを選ぶところまでだ。新しい記憶文を自然な言葉で書く、適切な粒度へ統合する、曖昧な時間表現を説明する仕事は生成系とコードに残る。さらにユーザーID・権限・記憶のsource・明示的な削除要求の扱いは、モデル判断ではなくアプリケーション契約である。

この分割が本当に有利かは自明でない。Jev用の別通信が増え、候補生成が先に失敗し、生成モデルとの境界で整合性チェックも必要になる。既存LLMに厳格なschemaを課すだけで十分かもしれない。あるいは削除・更新を避けて追加履歴を残し、検索時に現在性を解く設計の方が安全かもしれない。したがって比較するのは「現行LLM」「LLM＋より厳しい出力検証」「Jev判断＋同じ生成器」「追加型の記憶方式」であり、正解率だけでなく、誤対象ID、破壊的UPDATE/DELETE、後での検索品質、呼出回数と総時間を測る。

対象IDを選ぶ設計には候補生成の上限がある。old memoryが検索に現れなければ、Jevは誤ったIDを選ぶか、新規ADDと答えるしかない。retrievalのcandidate recallを上げる前に質問文を磨いても、真の正解は候補に入らない。同じ文字列の記憶が二つあれば、テキストを重複排除してIDの差を消してはならない。選択後、DBのrevisionが進んでいればIDと本文を再照合し、古い判断をそのまま適用しない。この再検証はJevへの不信ではなく、分散した読み書きの常識である。

道具選択を含むagentも似ている。「どの既知ツールを使うか」「画面上のどの既知要素を対象にするか」は閉じられるが、「ユーザーに何を説明するか」「検索語をどう作文するか」は閉じないことがある。操作・対象IDを選ぶJev結果が正しくても、ツール実行時に対象が移動していれば危険だ。executorはID、状態版、権限、引数制約を再確認する。逆にLLMが毎回道具まで選ぶ現行方式で十分なら、新しいモデル境界は単なる障害点増加に終わる。重要なのは生成モデルの存在でなく、**その中に評価可能な有限判断が混ざっているか**である。

生成器を残し、Jevを候補評価器にするパターンもある。複数の回答案をLLMが書き、Jevがrubricで選ぶとき、候補文そのものの正しさと評価スコアを混同しない。引用が多いだけの誤答が高得点になるなら、生成器が評価器の弱点を学んだ可能性がある。独立した人間評価や、コードによる根拠照合を固定しておく。Scoreを最適化して得た改善は、同じScoreで検証すると循環論法になりやすい。

この章の設計原則は「LLMをJevに置き換える」ではない。**一つの呼び出しを、選ぶ・書く・実行するに分解する**。選ぶ部分だけが閉じており、候補と副作用の境界を管理でき、追加のサービス負担より利益があるならJevを試す。そうでなければ既存LLMとコードを改善する方がよい。

## 11. 比較実験の設計――モデル単体ではなく「行動」を採点する

導入候補を挙げることと、採用できる証拠を作ることの間には大きな距離がある。テストしやすいのは、モデルが返したChoiceの一致率だ。しかし利用者に見えるのは、最終的に届いた通知、選ばれた日付、closeされたissue、見落とされたテストである。評価の単位をモデル応答へ狭めた瞬間、候補生成、呼出条件、fallback、ネットワーク障害の誤りが採点表から消える。本章ではその消えた部分を戻す。

### 一つの集合に全部を混ぜない

まず、対象の全母集団を定義する。検索rerankなら全検索要求、stale botなら一定期間に検討された全issue、差分通知なら差分が生じた全イベントだ。次に「Jevを呼ぶ条件」を通過した部分集合を記録する。`no-match`時だけ呼ぶ設計で、現行ルールが自信ありで誤った例は部分集合の外にある。モデル評価にその例を入れないと、条件付き精度が高くても全体の失敗を見逃す。呼出条件を独立した**選択器**として採点する理由はここにある。

選択肢をコードが生成する場合は、少なくとも三つの母数が必要になる。

1. **Candidate recall**：人手で認めた正解IDが候補集合に含まれた割合。
2. **Conditional decision quality**：正解IDが候補にある例の中で、モデルがそれを選び、または妥当に棄権した割合。
3. **End-to-end outcome**：呼ばれた例と呼ばれなかった例を合わせ、実際のアプリケーションが望ましい行動をした割合。

この三つを単純に一つの「accuracy」へ足してはならない。候補生成に失敗した例をモデル誤りへ数えると質問の改善で直せると誤解する。逆にモデルが正しく選んでも、古いIDを再検証せず誤った対象へ副作用を出したなら、E2Eは失敗である。抽出・検索・記憶更新の設計でこの区別は特に重要になる。

### ラベル付けも設計の一部

ゴールドラベルは既存システムの出力をそのままコピーしない。既存の誤りを真実として学び直すからだ。単純な例は、botがcloseしたissueを全て「closeが正しかった」とする誤りである。少なくとも境界の難しい例は、モデルの答えを見せずに人間がラベルを付け、意見の相違を記録する。曖昧な例に無理やり唯一の正解を押し付けるより、`UNCLEAR`や複数の許容行動を定義した方が製品判断として正直だ。

層化も必要だ。Sherlockならサイト別・response type別、メールなら言語とクライアント別、記憶更新なら同義・追記・矛盾・明示的forget別、issueなら最後の行動者とラベル別。ランダム分割だけでは、同じテンプレートが学習用と評価用へ跨り、モデルがそのサイトやメールクライアントを「理解した」ように見える。時間順・サイト単位・ユーザー単位のholdoutを、将来の利用分布に合わせて選ぶ。どの分割で得た数字かを報告しなければ、採用の根拠にならない。

### 代替案を弱く作らない

Jevと比べる決定論的ベースラインは、わざと貧弱な現在のコードではない。「この問題のために、同じ工数でできる最も安い改善」を含める。soft-404にはDOM selectorやサイト別fingerprint、返信境界には多言語marker、staleには役割と`needs-info`ラベル、releaseにはcommitlintとcustom rule、DOMにはXPathやlink densityの改善を置く。既存LLMの部分置換ならstructured-outputの厳格化を比較に入れる。これらが十分ならサービス境界を増やす必要はない。

同時に、決定論的改善が存在することだけでJevを不採用にしない。小さな規則改良は頻出ケースを救い、長い尾の言い回しやテンプレート変化はなお残るかもしれない。その残部へ選択的に呼ぶ設計なら、**現在の規則、改良規則、改良規則＋Jev**を同じholdoutへかける。ベースラインとモデルが互いに異なる誤りを犯すかを見る。両方が同じケースで失敗するなら「組み合わせれば解決」という期待は弱い。

### 損失表を先に書く

同じ不一致率でも行動の費用は大きく違う。例えば「在庫ありを見逃す」は機会損失、「存在しない在庫を通知する」は信頼損失だ。メールの新規返信を消せばサポート要求が未読になり、引用を残せば要約に古い要求が混ざる。記憶の誤DELETEは後の多くの回答へ波及し、余分なADDは検索ノイズを増やすが可逆性が高いかもしれない。どちらが重要かは利用者と用途で決める。モデルの平均一致率より、次のような**損失の非対称性**を先に文書化する。

| 用途 | 強く監視する誤り | 対照となる軽めの誤り | 採用時に必要な観測 |
| --- | --- | --- | --- |
| 重要変更通知 | 必要な変更を黙って抑制 | 余分な通知 | missed-alertと苦情、配信率 |
| 記憶の更新 | 誤IDへのUPDATE/DELETE | 冗長なADD | 後続検索の誤り、訂正履歴 |
| Stale issue | maintainer待ちの誤close | 不要issueの保留 | reopenと人手ラベル、保留負荷 |
| テスト選択 | 失敗するテストの未実行 | 余分なテスト実行 | 欠陥取り逃がし、CI時間 |
| 本文抽出 | 本文・captionの欠落 | boilerplate混入 | span recallと汚染率 |

閾値は、上の損失と実データから選ぶ。別案件のconfidence閾値を持ち込んでも、クラス分布、質問、候補集合、呼出条件が変われば意味は変わる。[公式のconfidence routing](https://docs.typesafe.ai/patterns/confidence-routing) はルーティング手法の参考だが、そこでの数字を採用閾値にしない。分布がずれたときの校正、棄権率、高confidenceの重大誤りを評価セットに残す。

### 遅延と費用は境界全体で測る

モデル呼び出しの中央値だけでは、システムの負担は分からない。候補生成、ネットワーク往復、リトライ、出力検証、fallback、ログと再評価、人間レビューを含める。対象一件あたりの呼出回数、payloadの大きさ、p50とp95のE2E遅延、timeout率、コスト、外部依存の増加を取る。選択的呼び出しなら、呼ばれない割合だけでなく、検出器の見逃しが利益を削る。オフライン再生で呼出数は見積もれても、本番の請求額やユーザー体感遅延は証明できない。著者が別環境で発表した改善率も移植できない。

実験は「勝つまで質問を直す」ものではない。開発集合で調整し、凍結した評価集合で一度判定する。失敗を見て改善したいなら新しい開発集合に移し、評価集合を再利用した事実を明記する。比較前に、少なくとも重大誤りの許容条件、単純ベースラインに勝つ必要、プライバシー・遅延の上限を記録する。採用条件を結果を見た後で変えると、検証ではなく宣伝になる。

## 12. 本番運用の境界――判断を行動へ変える前に

良いオフライン結果が出たとしても、実装上の責務は増える。モデル応答の型を検証し、候補外IDを拒否し、入力の版を照合し、タイムアウト時の具体的な行動を決め、再試行で副作用を二重実行させない。必要な認可はアプリケーション側で行う。これらは「LLM一般の注意」ではなく、**確率的判断を既存の決定的処理へ接続する際の境界**である。

次の疑似コードは、文書から抽出された候補IDを選ぶ場合の責務分離を示す。実際のJev API構文ではない。

```text
source = load_authorized_document()
revision = source.revision
candidates = deterministic_extract_with_spans(source)
if candidates.empty: return MISSING_EVIDENCE

proposal = judge(relevant_excerpt(source), candidate_ids(candidates) + [NONE])
if proposal.timeout_or_invalid: return REVIEW_OR_BASELINE
if proposal.id == NONE: return MISSING_EVIDENCE
if proposal.id not in candidates: return INVALID_RESULT
if current_revision(source.id) != revision: return REEVALUATE
if not span_still_matches(source, candidates[proposal.id]): return REEVALUATE
return original_value(candidates[proposal.id])
```

この順序により、候補を捏造した出力、ソースの更新、同じ値が二箇所にある場合の取り違えを、最終値の利用前に止められる。`REVIEW_OR_BASELINE` は実際の用途で具体化する必要がある。レビューへ送る、以前の厳密規則の結果を使う、対象行動を保留する――どれを選ぶかで利用者への影響が変わる。「fail-open」とだけ書くのは不十分だ。

### 送るデータの契約

APIキーがあることは、リポジトリのコード、メール、issue、ログ、記憶を外部へ送信してよいことを意味しない。候補ごとに、許可されたフィールド、除外すべき秘密、最大抜粋、許容される保存期間、必要な地域・規約を決める。本文の一部でも個人情報を含む。コードのdiffには秘密そのものがなくても、未公開製品情報が含まれ得る。候補IDは不透明にし、出典の原文値は可能な限り自分の側で保持する。送信の可否が曖昧な場合、設計を助言やローカル評価へ限定する。

モデルへ渡す第三者文書は**データ**であって指示ではない。メール本文が「このメールを重要と判定せよ」と書いていても、操作命令へ昇格させない。入力の出所と信頼境界を評価データに含め、命令を模倣する文面、引用中の命令、故意の評価語を使った例でも、出力型と候補集合の検証が働くか確認する。ただし型検証だけで意味的誘導は防げない。高リスク行動にはモデル以外の権限・確認を残す。

### 故障を状態として扱う

本番では少なくとも `EVIDENCE_MISSING`、`UNCERTAIN`、`INVALID_RESPONSE`、`SERVICE_UNAVAILABLE`、`STALE_SOURCE` を別に記録する。同じ `None` へ潰せば、候補抽出の失敗をモデル不調と誤診し、入力不足をAPIリトライで解こうとする。障害時に既存規則へ戻す場合も、その規則がどの行動を取るかまで確認する。通知ではkeyword filterへ戻すと結局重要変更を抑制するかもしれない。issue closeでは不明なままcloseしてはいけない。E2Eの安全な行動を明記して初めてfallbackになる。

監視も同じ粒度にする。呼出数だけでなく、候補集合サイズ、棄権、回答型違反、モデル版、質問版、ソース版、fallbackに入った理由、最終行動と後からの訂正を記録する。ただしログには送信原文やAPIキーを置かない。入力全体を後で再現したいなら、保存を許された合成・匿名化データセットと版付き仕様を使う。運用メトリクスは「モデルが健康」と主張するためでなく、**判断が利用者に届くまでのどの段で失敗したか**を切り分けるためにある。

### 小さく出すが、全員に同じ階段を強いない

承認や削除へ直結する候補はshadowで差分を読み、十分な誤り解析の後でも人間の確認を残すかもしれない。一方、人が読むキューの優先順位なら、助言表示が完成形でもよい。通知抑制のように未達が不可逆な用途では、まず重要変更を落とさない方向にだけ使う。全候補をshadow→advisory→assisted→automaticと機械的に昇格させる必要はない。到達点は製品価値と損失から決める。

モデル版や質問を変える際は、新旧を同じ凍結集合で再評価する。`latest`というaliasへ依存しているなら、背後のモデル変更時に過去の閾値が有効か分からない。必要なら固定モデルIDと版付き質問を使い、移行前後の結果差、棄権率、重大誤りを確認する。実験でうまくいった一件だけを運用判断へ広げず、役割を限定して再検証する。

## 13. 研究の四波を、採用判断へ戻す

四本の調査を順に読めば候補は増える。しかし増えた候補をそのまま機能リストにしてはいけない。初期調査は有限判断の形を広く見つける。第二波は置換以外の配置――sidecar、後段ゲート、競合解決、根拠整合――を示す。第三波はループ、保持、計算配分、探索といった制御平面を開く。第四波は具体的な弱いセンサーへ戻り、「情報がない」「決定性が価値」という非採用を強化する。これらは時系列の流行ではなく、**同じリポジトリを見る四つの焦点距離**だ。

一つのrepoを監査するなら、最初に目的と既存の利用者行動を読み、次に主要なデータフローを一つ最後まで辿る。判断らしい箇所で立ち止まり、どの波のレンズが役立つかを選ぶ。既存LLMがあるなら有限出力と自由文を分ける。ループがあるなら止める・残す・走らせる判断を調べる。規則やstatusがあるなら何の代理かを問う。いずれもコードの外側に消費者がいなければ、単にモデルを挿せるだけの場所だ。実在する利用者価値まで結びつかない候補は、提案の優先順位を下げる。

最終的な提案カードは短くてよいが、その裏側の思考は短くしない。少なくとも「固定したソース版と判断点」「現行動作と観測された限界」「提案する有限判断と呼出条件」「残す決定的処理」「安い代替」「誤りの非対称性」「障害時の行動」「反証できる評価」を揃える。計測がない効果は期待として書き、現行動作を読めなかった箇所は未調査として書く。Jevを導入しない結論も、十分なコード観察と比較があれば、曖昧な導入案より価値が高い。

ここまでで、候補を見つけてから採用可否を問う地図は揃った。最後に、短い質問と共有stateがその境界を壊さないかを点検し、三つの設計例で一連の判断を通してみる。

## 14. 質問とstateを設計する――短い問いほど周辺設計が要る

Jevの質問は長い仕様書ではない。だが短ければよいわけでもない。誤った対象を見たまま「正確に」答える質問、相対比較を絶対的な適合と取り違える質問、複数の条件を混ぜて誤りの原因を隠す質問は、文面だけ流暢でも設計失敗である。[公式のprimitives](https://docs.typesafe.ai/primitives) は一問一判断と独立した質問を基本にしている。実務では、その問いを支えるstateと後段のコードこそ難所になる。

### 共通stateの誘惑

同じリクエストへ複数の質問を載せれば、ネットワーク往復をまとめられる。しかし全質問が同じstateを見る。例えば一件のサポートticketについて「返金を求めているか」と「文面が怒っているか」を尋ねるなら、共通のticket本文は自然だ。一方、「候補Aが請求日か」を問うためにAの周辺行をstateの最上位へ強調し、別の質問で候補Bを問うと、Bの判断までAの文脈に引かれ得る。特定質問だけに必要な抜粋はそのinstructionsへ明示するか、質問を分ける。速さを得るためのバッチが、質問間の汚染を作らないかを検証する。

質問Aの答えで質問Bの候補集合が変わるなら、同じリクエスト内の二問にしてはいけない。例えば先にツール種別を選び、そのツールに存在する引数名だけを次に選ぶ場合、後段候補は前段回答を見て作る。逆に「返金要求か」と「顧客は怒っているか」は独立して問える。遅延削減のために偽の独立性を作ると、存在しない引数や誤ったツール対象を許す。独立・依存の判定は質問文ではなく、**後段候補集合が前段回答なしに定義できるか**で行う。

### Choiceの`none`は事後的な逃げ道ではない

候補集合から最良を選ばせるChoiceは、候補のどれも正しくない世界をそのままでは表せない。出典付き日付抽出なら、文書にある日付がすべて納期で、要求された発行日がないことがある。候補一件でも同じだ。`none_of_the_above`を明示し、候補生成の欠落と「候補はあるが適合しない」という判断を別に記録する。全候補が不適切でも分布の合計は一になる。最大確率が高いだけで適合を主張しない。

Scoreは順序のあるrubricを表し、Noulはyes/noの確率を表す。例えば「この変更は通知すべきか」というNoulと「変更の重大度」を段階評価するScoreは、同じ値域へ揃えて比較できない。Choiceの候補間確率も別の質問のNoulと同一の校正を保証しない。閾値を併用するなら、それぞれの意味と評価集合を固定し、コードが合成する規則を記録する。「confidenceが高いから公開してよい」ではなく、「どの損失の下で、どの行動を自動化するか」を決める。

### 質問文の版はコードの版と同じくらい重要

stateの項目名、候補ラベル、criteriaの説明、モデルID、後段閾値を変えると、同じ入力でも結果は変わり得る。A/B実験で質問を調整するなら変更点を一つずつ記録し、評価集合を固定する。コードだけcommitして質問文をダッシュボードで黙って変更する運用では、事故時に何が変わったか追えない。候補の説明文に商品名やチーム名を入れた場合、その命名が変わるだけでも基準の再確認が必要になる。

文脈の少なさと多さの両方に罠がある。短すぎれば`"fix stuff"`からSemVer影響を推測できない。長すぎれば無関係なコメントや攻撃的指示が判断を揺らす。最小stateは固定文字数ではなく、**その判断に必要な区別を残す最小情報**である。ある候補で判断材料が不足するなら、無理に`UNKNOWN`を減らすより、許可された追加観測や人手経路を検討する。

## 15. 紙の上で導入案を壊す――三つの検討例

以下は実製品の測定値ではなく、設計の弱点を見つけるための架空の検討例である。各例を読んだら「Jevへ何を送るか」より先に、**どの入力で案が壊れるか**を考えるとよい。

### 検討例A：発行日を選ぶ

請求書から発行日を返す処理が、最初の正規表現一致を採っているとする。紙面には`2026-09-01`が注文日、`2026-09-05`が発行日、`2026-10-05`が支払期限として出る。正規表現は三つとも正しく抽出している。失敗は抽出ではなく、**役割を見ず最初を採る選択**にある。候補をID、原文値、周辺ラベル、source spanで保持し、Choiceで`issue_date`に対応するIDか`none`を選ぶ提案なら、Jevの役割は明確だ。日付文字列を新しく生成させたり、期限計算を任せたりしない。

だが次のページでは「発行日」の印字がなく、唯一の日付が納期かもしれない。候補が一つだから正解、とはしない。さらにOCRが発行日を読み落とした場合、モデルには選択肢がない。前者は適合判断、後者は候補生成の失敗である。評価表では両者を別行に置く。選択後にsource spanから原文を返し、文書のrevisionが変わったら再判断する。既存のラベル辞書を拡張するだけで同等ならJevは不採用。[公式のpre-parsed extraction](https://docs.typesafe.ai/cookbooks/pre_parsed_value_extraction_cookbook) はこの候補選択の構図を示すが、この架空の請求書の性能を保証しない。

### 検討例B：重大変更だけ通知する

ある購読者は「価格が下がったら知りたい」と指定した。監視ページの差分には価格表示、広告文、更新日時が含まれる。単純な`text_changed`で全て通知すると騒がしい。一方、モデルが`NOT_RELEVANT`と答える度に通知を消すなら、価格低下の取り逃がしが危険になる。最初の設計では価格を構造的に抽出できるページは数値比較で処理し、構造化できない差分だけ意味的に判断する。Jevが不確か・不通なら、変更を配信するかレビュー待ちに残す。`価格低下のみ`という利用者条件と、モデル出力に実際の金額が書かれたかを混同しない。

ベースラインは「全変更通知」だけでは弱すぎる。CSS selectorで価格欄を固定し、抽出値を比較する案も含める。評価では購読者が重要と判断した変更を人手でラベル付けし、通知数、重大見逃し、購読解除、人手確認時間を別に測る。ページの価格欄がそもそも取得できない日には、意味判断に進まず観測失敗として記録する。差分が正しいことと、通知すべきことは違う。この二段を分けるのが後段ゲートの価値だ。

### 検討例C：記憶を消すか、残すか

利用者が「以前の住所はもう使っていない」と述べたとする。古い記憶の一つに住所があり、別の記憶には同じ町にある勤務先がある。候補検索は両方を返した。`DELETE`のChoiceだけを問うと、何を消すのかが曖昧だ。遷移の種類と対象IDを分け、候補IDの意味・作成時期・利用者スコープをstateへ含める。選ばれたIDが元記憶と同じrevisionであることをコードが確かめる。それでも、明示的な忘却要求をどう扱うかは利用者の権限・製品ポリシーであり、Jevが決めるものではない。

比較案には既存LLMのstructured output改善に加え、「古い記憶を消さず履歴へ残し、検索時に現在性を決める」設計を置く。もし削除の誤りが重大なら、モデルは候補の提示までで、人間や別の確実な手続きが最終決定する。新文面の生成が必要なら、別の生成器が書き、元事実との一致を検査する。部分置換は構図として美しくても、呼出回数と同期点が増えて実運用では負けるかもしれない。美しいアーキテクチャではなく、最終行動の損失と負担で裁く。

三例とも、最初の質問は「どのprimitiveを使うか」ではなかった。選ぶべきものがソースにあるか、消費者がどう行動するか、単純な規則がどこまで届くかを確かめてから、初めて質問型が決まる。これは一連の検討に共通する観点でもある。

## 結論――提案できることと、見送れること

ここで示した候補には、Jevで解ける可能性のあるものと、明確に導入しない方がよいものが混在する。それは欠点ではない。Sherlockの同一内容ページには判別情報がなく、Blackの再現可能性は確率化によって壊れる。Vectorの高頻度経路では通信予算が成立しないかもしれない。現行の規則を少し直すだけで十分な製品もある。こうした非採用を、コードを読んだ理由付きで言えることが導入提案の品質を上げる。

一方で、既存のLLMや分類器がなくても、自然文を扱うrule engine、差分通知、文書抽出、issue管理、検索の終了条件には意味判断が埋まる。置換か追加か、常時か曖昧時だけか、行動か助言かは利用者の価値と損失で決める。Jevの能力から逆算して用途を探すのでなく、実際のデータフローから必要な小判断を切り出す。その判断の選択肢・入力・権限・失敗時動作を固定し、単純な代替案と同じデータで比べる。

結論は一つのモデル名ではなく、再現できる意思決定になるべきだ。**どの判断を、なぜそこへ、何を残して、何と比べ、どんな失敗なら撤回するか。** それを説明できる候補だけを実装する。説明できない候補は、追加調査か見送りに戻す。四波の調査を一冊へ統合する目的は、Jevを多く使わせることではなく、使うべき一点と使わない境界を同じ精度で見極められるようにすることにある。
